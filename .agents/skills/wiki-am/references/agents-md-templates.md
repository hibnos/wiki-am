# wiki/AGENTS.md 작성 가이드 (프로젝트 유형별)

`wiki-{service}/wiki/AGENTS.md`는 이후 모든 LLM 세션이 따르는 위키 운영 규칙이다.
아래 **공통 골격**을 바탕으로, 프로젝트 유형별 조정 지침에 따라 실제 프로젝트에 맞게 구체화해서 작성한다. 그대로 복사하지 말 것 — `{service}`, 유형별 분류, ingest 대상, "답해야 하는 질문"을 반드시 실제 값으로 채운다.

## 공통 골격

```markdown
# wiki-{service} 위키 운영 규칙

이 위키는 Karpathy의 LLM Wiki 개념 기반이다.
Reference: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f

프로젝트 유형: **{유형}** — {이 프로젝트가 무엇인지 한 줄}.
이 위키가 답해야 하는 질문은 다음과 같다:
- "{이 도메인에서 사람들이 실제로 찾아보게 될 질문 1}"
- "{질문 2}"
- "{질문 3}"

## 원칙
- `../raw/`는 불변 원본이다. 절대 수정하지 않는다. 파일명은 `YYYY-MM-DD-출처-제목` 으로 넣는다. 위키(`wiki/` 이하)는 LLM이 전적으로 작성·유지한다.
- 모든 주장은 출처(raw 파일 또는 코드 경로)를 링크한다. 모순을 발견하면 숨기지 않고 그 페이지에 `> ⚠️ 모순:` 블록으로 양쪽 주장·출처·상태(미해결/해결)를 적는다. 최신 정보가 항상 옳지는 않으므로 조용히 덮어쓰지 않는다.
- `confidence` 는 소스·시스템에서 직접 읽은 사실이면 `verified`, 의도·이유를 역산한 것이면 `assumed` 다. `assumed` → `verified` 승격은 `sources` 에 확인 근거 경로를 추가할 때만 한다.
- 페이지는 고립 문서가 아니다 — 관련 페이지끼리 연결한다. 프론트매터 `related` 에는 ID 만, 본문에는 상대 링크.
- 페이지의 계층·ID·프론트매터 규칙은 `../SCHEMA.md` 가 정본이다. 새 페이지는 `../templates/{type}.md` 를 복사해 시작하고, ID 는 `python3 ../scripts/lint.py next-id {PREFIX}` 로 발급하며, `{{ }}` 자리표시자는 전부 채운다. 파일명은 내용을 말하는 슬러그로 짓고 ID 는 프론트매터에만 둔다.
- 참조는 상위 계층 → 하위 계층 방향으로만 건다 (분석 → 엔티티 → 소스). 하위가 상위를 링크하지 않는다. 역방향은 `lint.py backlinks` 가 만드는 "참조됨" 블록으로 본다.
- 시점형(frozen) 페이지는 만든 뒤 본문을 고치지 않는다. 바뀌면 새 페이지를 만들고 `supersedes:` 로 잇고, 옛 페이지는 `status: superseded`·`superseded_by:` 두 필드만 바꾼다. index 에서는 옛 페이지를 카테고리 절에서 빼고 맨 아래 `## 대체된 페이지` 절에 `→ 새 ID` 와 함께 한 줄로 옮긴다.

## 구조
- 폴더·접두어·계층·페이지 종류(living/frozen)의 정본은 `../SCHEMA.md` 다. 아래 목록은 그것과 1:1 이며 역할 설명이다.
- `index.md` — 전체 페이지 카탈로그. 질문에 답할 땐 여기부터 읽는다. 페이지를 만들거나 지우면 반드시 갱신한다. 대체된(superseded) 페이지는 맨 아래 `## 대체된 페이지` 절에만 둔다.
- `log.md` — append-only. 형식: `## [YYYY-MM-DD] <작업종류> | <대상>` (작업종류: init/ingest/update/lint/schema)
- `overview.md` — 서비스 전체 그림. 큰 변화가 ingest되면 갱신한다.
- `{하위폴더1}/` — {역할. 페이지 단위와 필수 섹션}
- `{하위폴더2}/` — {역할}
- (유형별 하위 폴더는 아래 지침을 따라 **한 줄에 하나씩** 이 형식으로 나열한다. `sources/`·`analyses/` 는 모든 유형에 있다.)

## 워크플로우
### Ingest (새 소스/변경 반영)
1. 소스를 읽고 핵심을 파악한다. 같은 주제의 페이지가 이미 있는지 index 와 grep 으로 먼저 찾는다.
   - 같은 개념·같은 엔티티의 living 페이지면 제자리 갱신한다. 같은 소스의 frozen 요약은 내용이 바뀌면 새 페이지로 대체한다. 같은 주제라도 관점이 다르면(예: 설계 문서와 구현 문서) 별도 페이지다.
   - 애매하면 새로 만들지 말고 사용자에게 묻는다 — 중복을 나중에 병합하는 비용이 묻는 비용보다 크다. 질문은 사용 가능한 사용자 입력 도구로 하되 현재 모드에서 지원하지 않으면 일반 대화로 묻고, "기존 페이지(ID) 갱신 / 새 페이지 생성" 처럼 선택지를 제시한다.
2. 소스 요약 페이지(frozen)를 템플릿에서 만들고, 영향받는 엔티티/개념 페이지(living)를 제자리 갱신한다. `updated` 는 내용을 실제로 바꿨을 때만 올린다 (오타 수정 제외).
3. `related` 와 링크를 방향 규칙대로 걸고 index.md를 갱신한다.
4. `python3 ../scripts/lint.py lint` 로 ERROR 0 을 확인하고 `backlinks` 를 갱신한 뒤 log.md에 기록한다.

### Query (질문 답변)
1. index.md → 관련 페이지 순으로 읽는다.
2. 답은 확인됨(페이지 ID 근거) / 확인 필요(위키에 없음) / 가정(추론, 근거 명시) 을 구분해 적고 셋을 섞지 않는다.
3. 답이 위키에 없는 가치 있는 종합이었다면 analyses/에 새 페이지로 남긴다. 기준은 하나 — 3개월 뒤 누군가 이걸 찾을 것인가. 아니면 적지 않는다.

### Lint (주기 점검)
1. `python3 ../scripts/lint.py lint` — ERROR 는 반드시 해소한다. WARNING 은 사유가 있으면 남기고 그 사유를 페이지에 적는다 (억지로 0건을 만들려고 의미 없는 링크를 만들지 않는다).
2. 스크립트가 못 보는 것을 읽어서 찾는다: 모순, 낡은 주장, 출처와 어긋나는 서술.
3. `python3 ../scripts/lint.py backlinks` 로 파생 블록을 갱신하고 log 에 기록한다.

### 이관 (위키 밖에서 만든 기존 문서를 들일 때)
1. 사용자가 이관을 요청한 원본을 `../raw/` 에 새 파일로 복사해 보존한다. 기존 raw 파일은 덮어쓰거나 수정하지 않는다. 옮기는 과정에 해석이 들어가므로 되돌릴 자리가 필요하다.
2. 옛 ID 와 옛 이름은 프론트매터 `aliases` 에 보존한다.
3. ID 변경은 이관 시점이 마지막 기회다. 이관이 끝난 뒤에는 바꾸지 않는다.
```

"답해야 하는 질문" 3개는 하위 폴더 설계의 근거다 — 각 질문에 답하려면 어느 폴더의 어떤 페이지를 열게 되는지가 곧 구조다.

아래 유형별 폴더의 접두어·계층·living/frozen 은 `schema-and-templates.md` §5 표에 있다. Step 3b 가 그 표로 `SCHEMA.md` 를 만든다.

## 유형별 조정 지침

### 서비스형 공통 (msa service · monolithic service · batch 에만)
아래 세 유형의 AGENTS.md 워크플로우에는 `### 첫 채움 (기존 코드베이스를 처음 들일 때)` 절을 넣는다. research·library/tool·skill·prompt 개발에는 넣지 않는다.
- 레포 전체를 ingest 하지 않는다. 질문 또는 변경 대상에서 바깥으로(outside-in) 필요한 만큼만 채우고, 두 다리를 넘지 않는다.
- 시스템에서 읽히는 것(라우팅·설정·스키마·코드 경로)을 먼저 적는다. "왜 그렇게 만들었나" 는 `confidence: assumed` 로 적는다.
- 코드와 문서가 다르면 코드가 사실이다. 단 문서를 조용히 덮어쓰지 않고 모순 블록으로 기록한다 — 문서가 원래 의도였을 수 있다.
- 실제 코드·DB 구조·API 스펙·운영 환경·장애 원인은 확인 없이 서술하지 않는다. 모르면 `확인 필요` 로 남긴다.
- 완벽한 첫 채움을 기다리지 않는다 — 첫 질문에 답할 만큼이면 시작한다.

### msa service
- 하위 폴더: `services/`(서비스별 페이지: 책임, API 계약, 의존 서비스), `concepts/`(도메인 개념·상태머신), `operations/`(배포 선행조건, 인프라, 장애 이력), `analyses/`, `sources/`
- 엔티티의 중심은 **개별 마이크로서비스와 서비스 간 계약**이다. 서비스 페이지에는 upstream/downstream 의존 관계를 반드시 명시하게 한다.
- ingest 대상 예시: API 스펙 변경, 신규 서비스 추가, 배포 절차 문서, 장애 회고(postmortem).
- 첫 채움·정본 우선순위: 위 서비스형 공통 절을 넣는다.

### monolithic service
- 하위 폴더: `modules/`(모듈/도메인별 페이지), `concepts/`(도메인 개념·상태머신·비즈니스 규칙), `operations/`(배포, 마이그레이션), `analyses/`, `sources/`
- 엔티티의 중심은 **내부 모듈과 도메인 경계**다. 모듈 간 결합(공유 테이블, 공통 코드)을 페이지에 드러내게 한다.
- ingest 대상 예시: 도메인 규칙 문서, 스키마 변경, 리팩터링 결정 기록.
- 첫 채움·정본 우선순위: 위 서비스형 공통 절을 넣는다.

### batch
- 하위 폴더: `jobs/`(잡별 페이지: 스케줄, 입출력, 재실행 조건, 실패 시 영향), `dataflows/`(데이터 흐름·계보), `operations/`(운영 절차, 장애 대응), `analyses/`, `sources/`
- 엔티티의 중심은 **잡과 데이터 흐름**이다. 잡 페이지에는 선행 잡/후행 잡 의존성과 멱등성 여부를 반드시 적게 한다.
- ingest 대상 예시: 신규 잡 추가, 스케줄 변경, 데이터 소스 변경, 배치 장애 이력.
- 첫 채움·정본 우선순위: 위 서비스형 공통 절을 넣는다.

### research
- Karpathy 원형에 가장 가깝다. 하위 폴더: `sources/`(논문·아티클 요약), `entities/`(연구자, 조직, 도구, 데이터셋), `concepts/`(이론, 방법론), `analyses/`(비교·종합)
- 엔티티의 중심은 **논문/소스와 개념**이다. 소스 하나를 ingest하면 관련 개념·엔티티 페이지를 폭넓게 갱신하게 한다 (관련성이 있는 페이지만; 고정 개수를 채우지 않는다).
- ingest 대상 예시: 새 논문, 실험 결과, 블로그/아티클.

### library/tool
- 라이브러리·SDK·CLI 도구처럼 **남이 가져다 쓰는 코드**다. 하위 폴더: `api/`(공개 API 단위별 페이지: 계약, 제약, 사용 예, 흔한 오용), `concepts/`(핵심 추상화·설계 원칙), `decisions/`(설계 결정·호환성 정책·폐기(deprecation) 이력), `analyses/`, `sources/`
- 엔티티의 중심은 **공개 API 표면과 버전 간 호환성**이다. api 페이지에는 도입 버전·변경 이력·대체 API 를 반드시 적게 하고, 브레이킹 체인지는 decisions/ 에 근거와 함께 남기게 한다.
- ingest 대상 예시: 릴리즈 노트, 브레이킹 체인지 PR, 이슈·토론에서 확정된 설계 결정, 사용자 피드백.

### skill·prompt 개발
- Codex 스킬, 시스템 프롬프트, 에이전트 정의처럼 **LLM 의 행동을 정의하는 산출물**을 만들고 튠하는 프로젝트다. 하위 폴더: `skills/`(스킬·프롬프트별 페이지: 목적, 트리거 범위(발동/미발동 예시, 인접 스킬 경계), 구조, 버전 이력, 알려진 약점), `patterns/`(여러 스킬에 걸쳐 재사용되는 설계 패턴 — 언제/왜/적용 스킬/반례), `evals/`(평가 기록 `YYYY-MM-DD-<skill>-<주제>.md`: 프롬프트 세트, 기대/실제, 실패 분석, 그로 인한 변경), `analyses/`, `sources/`
- 엔티티의 중심은 **스킬과 그 평가 결과**다. 스킬의 *현재 상태*는 SKILL.md 원본이 정본이고, 위키는 배경·이력·결정 근거·평가를 담는다 — SKILL.md 를 위키에 통째로 복사하지 않게 한다. 워크플로우에 **Eval** 을 추가한다: description 이나 워크플로우를 바꿨으면 발동/미발동 프롬프트 세트로 재검증하고 evals/ 에 남긴 뒤 skills/ 페이지 버전 이력에 링크한다.
- ingest 대상 예시: SKILL.md/description 변경(변경 이유 포함), 평가 실행 결과, 공식 스펙 문서, 사용자 피드백 로그.

### 그 외 유형
사용자가 위 6개 외의 유형을 답하면, 그 도메인에서 "질문받았을 때 찾아보게 될 지식 단위"가 무엇인지 생각해서 하위 폴더를 설계한다. 위 6개 중 가장 가까운 유형이 있으면 그 지침을 출발점으로 삼는다. 공통 골격(index/log/overview + ingest/query/lint + "답해야 하는 질문")은 유지한다.
